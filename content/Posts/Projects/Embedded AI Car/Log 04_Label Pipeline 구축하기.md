## 들어가며

[[Log 03_Lane Model 적용 가능성 검증|지난 포스팅]]에서는 CULane으로 학습된 CLRKDNet을 프로젝트 맵 이미지에 적용해봤다. 공식 추론 과정을 다시 맞춘 뒤에도 모델은 실내 맵의 노란 레인에 거의 반응하지 않았다. 이 문제는 학습 도메인의 차이였던 것을 확인했으니, 이제 fine-tuning을 시도해야 한다.

근데 모델을 다시 학습하려면 이미지뿐 아니라 정답이 필요한데, 이 정답 형식을 내가 가져온 모델에 맞춰서 생성해야 한다. 파인튜닝 전, **레이블링**이라는 새로운 문제가 생겼다.

## 1. 맵 데이터 수집 방식

Fine-tuning과 레이블링 작업을 하기 위해 데이터부터 모았다.

처음 현장에서 모은 lane 이미지는 1,360장이었다.
자동차를 직선과 곡선, 교차로의 여러 위치에 놓고 촬영했기 때문에 domain gap을 확인하기에는 충분했다. 근데 장면별로 정돈해서 촬영한 이미지가 많아서, 자동차가 움직일 때 나타나는 시점 변화를 모두 담지는 못했다.

그래서 추가 수집에서는 노트북의 방향키로 자동차를 직접 조종하면서 카메라 프레임을 0.25초 간격으로 자동 저장했다. 촬영 중에는 직선, 곡선, 좌우 편향, 교차로와 같은 장면 정보도 함께 기록했다.

| 데이터 | 규모 | 수집 방식 | 주요 용도 |
|---|---:|---|---|
| 초기 맵 이미지 | 1,360장 | 자동차를 여러 위치에 배치해 촬영 | domain gap 확인과 초기 레이블 생성 가능성 확인 |
| 확장 lane 데이터 | 2,467장 | 원격 조종 중 일정 간격으로 자동 저장 | label 추출 방법과 pipeline 검증 |

확장 데이터에는 중앙에서 바라본 정돈된 직선뿐 아니라, 한쪽 레인이 크게 보이는 경우와 코너를 가까이서 바라보는 경우, 여러 노란 선이 동시에 나타나는 교차로도 포함했다. 학습 데이터를 그냥 늘리는 것보다 **모델이 실제로 마주칠 카메라 구도**를 생각하며 늘려 나갔다.

![[embedded_ai_car_log04_scene_grid.png]]

> 수집 데이터에 포함한 대표 장면. 직선과 좌·우 곡선뿐 아니라 편향된 시점, 교차로와 hard case(어려운 장면)까지 함께 남겼다.

## 2. CULane Label Format과 좌표계

우리 domain에 맞는 데이터는 모았으니, 이제 fine-tuning을 위해 우리 Lane model인 CLRKDNet이 학습된 데이터의 형식에 맞춰 레이블링을 해야 한다. 그리고 당연히 이 레이블링은 수작업으로 하는 건 불가능하니깐 패턴이나 규칙을 수립해서 파이프라인으로 만들어야 한다. 다시 말해, pseudo-label을 생성하는 작업이다.

이를 위해선 일단 CLRKDNet 모델은 **어떤 정답**을 기대하는 지 파악해야 한다.
### 2.1. CULane Label 구성

CULane은 이미지마다 `left`나 `right` 같은 클래스를 하나 붙이는 데이터셋이 아니다. 하나의 레인을 여러 `(x, y)` 좌표로 연결한 **polyline**으로 표현한다.

CLRKDNet 학습에 필요한 파일은 크게 세 종류다.

| 구성 | 역할 |
|---|---|
| `.lines.txt` | 한 줄에 하나의 레인을 `(x, y)` 좌표열로 기록 |
| Lane mask | 각 픽셀이 어느 레인에 속하는지 표시 |
| Train/validation list | 이미지와 mask의 위치, 데이터 분할 정보 기록 |

### 2.2. 원본 이미지 기준 좌표계

디스크에 저장하는 레인 좌표의 경우, resize된 모델 입력이 아니라 **원본 카메라 이미지 좌표** 기준이기 때문에 상단 crop과 `800×320` resize는 데이터를 불러온 뒤 수행했다. 레이블을 이미 잘라낸 이미지 기준으로 저장하면 학습 과정에서 좌표가 다시 변환되어 위치가 어긋나는 문제가 생긴다.

먼저 공식 데이터 로더가 이미지, `.lines.txt`, mask를 어떻게 함께 읽는지 확인하고, 프로젝트 카메라의 `1296×972` 좌표계에 맞춰 데이터 형식을 다시 정리했다.

![[embedded_ai_car_log04_label_triptych.png]]

> 같은 프레임의 원본 이미지, 노란색 mask, CULane 형식 polyline. Binary mask를 그대로 사용하는 것이 아니라 레인별 좌표열과 학습용 mask로 다시 구성했다.

## 3. HSV Mask에서 Lane Polyline까지

### 3.1. HSV 기반 노란 영역 추출

프로젝트 맵은 회색과 초록색 바닥 위에 노란 선이 그려져 있다. 실제 도로보다 색상 조건이 단순했기 때문에 HSV 색 공간에서 노란 영역을 비교적 쉽게 분리할 수 있었다.

그렇다고 색 공간 threshold 하나를 바로 고를 수는 없어서, sweep을 진행했다.
범위를 넓게 잡으면 바닥과 주변 물체까지 mask에 포함됐고, 너무 좁게 잡으면 조명이나 시점이 달라질 때 차선이 끊겼다. 여러 후보를 비교한 뒤, 배경 침입이 적은 보수적인 범위를 선택했다.

![[embedded_ai_car_log04_hsv_compare.png]]

> 동일한 맵 이미지에 서로 다른 HSV 범위를 적용한 결과. 넓은 범위는 차선 이외의 영역까지 포함했고, 최종적으로는 노란 차선 성분을 비교적 일관되게 남기는 설정을 사용했다.

### 3.2. Binary Mask 기반 Lane Polyline 추출

색 공간 범위를 이용해서 Binary Mask 추출은 했다.
근데 이 binary mask에는 어느 픽셀이 노란색인지만 들어 있기 때문에, 교차로처럼 노란 선이 여러 방향으로 나뉘거나, 한 차선이 화면 중앙을 넘어가는 장면에서는 mask만으로 좌·우 레인을 바로 구분할 수 없다.

Binary mask를 lane polyline으로 바꾸는 방법은 크게 세 계열로 순차적으로 실험하며 비교했다.

==Row-wise Extraction: 행 단위로 좌·우를 나누기==

각 높이에서 노란 영역을 찾고, 화면 중앙을 기준으로 가장 가까운 왼쪽과 오른쪽 점을 선택하는 방식이다. 구현이 단순하고 두 선을 자주 확보할 수 있었다. 여기에 곡선 fitting을 적용하면 울퉁불퉁한 좌표도 매끄럽게 만들 수 있었다.

근데 이 방식은 높이 y마다 점을 독립적으로 고르기 때문에, 곡선이나 교차로에서는 서로 다른 물리적 선의 점이 하나의 곡선으로 이어지거나, 같은 노란 영역이 좌·우 두 레인으로 나뉘기도 했다. 곡선을 매끄럽게 만드는 것과 올바른 선을 연결하는 것은 다른 문제였다.

==Sliding-window Tracking: 이전 위치를 따라가기==

두 번째 방법은 이미지 아래쪽에서 레인을 찾은 뒤, 이전 위치와 가까운 노란 영역을 위쪽까지 따라가는 방식이다. 차선이 명확하게 이어지는 구간에서는 행 단위 선택보다 자연스러운 곡선을 만들었다.

근데 교차로에서는 어느 분기를 따라가야 할지 기준이 모호했다. 한 번 다른 노란 선을 선택하면 그 방향을 계속 따라가면서 현재 주행 레인과 관계없는 곡선을 만들 수 있었다.

==Connected-component Fitting: 연결된 영역을 하나의 후보로 보기==

마지막 방법은 mask에서 서로 이어진 노란 영역을 먼저 구분하고, 각 영역의 중심점을 곡선으로 근사하는 방식이다. 같은 영역 안에서 점을 모으기 때문에 서로 다른 선을 높이마다 이어 붙이는 문제를 줄일 수 있었다.

대신 노란 선이 끊기거나 한쪽 레인이 충분히 보이지 않으면 두 선을 억지로 만들지 않았다. Coverage는 낮아질 수 있지만, pseudo-label에서는 애매한 두 선을 생성하는 것보다 한 선만 남기는 편이 안전하다고 판단했다.

![[embedded_ai_car_log04_method_compare_curve.png]]

> 같은 곡선 장면에 행 단위 기본형과 곡선 fitting, 연속 추적, 연결 영역 기반 추출을 적용한 결과. 같은 mask에서도 점을 묶는 방법에 따라 최종 polyline이 달라졌다.

## 4. Pseudo-label 추출 방식 비교와 선택

추출 방식의 차이는 교차로와 급한 곡선에서 더 뚜렷했다. 노란색 mask 자체는 잘 만들어져도, 멀리 있는 가로 방향 선이나 갈라지는 분기를 현재 차선과 연결하면 학습용 정답으로 사용하기 어렵다.

![[embedded_ai_car_log04_method_compare_complex.png]]

> 교차로와 hard case의 방법별 결과. 노란 영역이 여러 방향으로 이어질 때는 더 많은 선을 찾는 것이 반드시 더 좋은 레이블을 의미하지 않았다.

최종 결정은 일부 대표 이미지에만 의존하지 않고, 확장 lane 데이터 2,467장 전체에 각 방식을 적용해 비교했다.

| 방법 | 두 레인을 만든 비율 | 같은 영역을 두 레인으로 나눈 비율 | 레인 교차 비율 |
|---|---:|---:|---:|
| 행 단위 + 곡선 fitting | 87.4% | 29.2% | 8.3% |
| 연속 추적 + 곡선 fitting | 80.8% | 23.2% | 10.9% |
| 연결 영역 + 곡선 fitting | 64.0% | 0.0% | 4.6% |

연결 영역 기반 방식은 두 레인을 만드는 비율이 가장 낮았다. 그래도 동일한 노란 영역을 서로 다른 두 레인으로 나누는 경우는 없었고, 두 선이 교차하는 비율도 가장 낮았다.

물론 사람이 그린 정답이 없으니, 이 수치가 실제 정확도를 의미하지는 않는다. 그냥 **pseudo-label 내부의 일관성과 위험 신호** 정도로 보면 된다. 이 기준으로 보면 결론은 하나였다. 많이 찾는 방식보다 잘못된 두 선을 덜 만드는 방식이 학습 레이블에 더 적합하다는 것.

최종적으로 mask의 연결 성분을 구분한 뒤 각 성분을 2차 곡선으로 근사하는 방식을 선택했다.

## 5. 재사용 가능한 Label Pipeline

### 5.1. Dataset Builder의 처리 흐름

추출 방식을 정한 뒤에는 일회성 실험으로 끝내지 않고, 새로운 현장 데이터에도 다시 레이블링을 바로 적용할 수 있게끔 dataset builder로 분리했다.

전체 흐름은 다음과 같다:

```text
수집 manifest
→ 원본 이미지 확인
→ 주행 영역에서 HSV mask 생성
→ 연결 영역 기반 lane polyline 추출
→ quality gate
→ 이미지·.lines.txt·lane mask 저장
→ train/validation list와 검증 리포트 생성
```

### 5.2. Quality Gate와 최종 Dataset

내가 설정한 이 Quality gate는 좋은 레이블을 완전히 보증하는 것은 아니다. 레인이 하나도 없거나, 좌표가 지나치게 짧거나, polyline이 원래 mask와 거의 겹치지 않는 것처럼 **명확하게 깨진 결과만 자동으로 제외**하도록 했다.

교차하거나 가까워진 두 선은 바로 reject하지 않았다. 교차로에서는 실제 mask 자체가 복잡할 수 있기 때문이다. 이런 장면은 삭제하는 대신 검토 우선순위를 높여 overlay에서 확인할 수 있게 했다.

확장 lane 데이터 2,467장 중에서는 2,396장이 최소 조건을 통과했고, 레인이 검출되지 않거나 좌표가 최소 조건을 충족하지 못한 71장은 제외됐다. 이후 같은 카메라와 맵에서 다른 모듈을 위해 촬영한 원본 중 노란 레인이 보이는 프레임도 학습 후보에 포함했다.

| 처리 단계 | 이미지 수 |
|---|---:|
| 전체 학습 후보 | 9,284장 |
| Quality gate 통과 | 9,052장 |
| Train | 7,241장 |
| Validation | 1,811장 |

Builder는 각 이미지의 `.lines.txt`와 lane mask를 생성하고, 학습 목록을 8:2로 분할한 뒤 파일 경로와 이미지 크기, mask와 label의 대응 관계도 검사했다. 형식 검증에서는 누락되거나 맞지 않는 항목이 발견되지 않았다.

![[report_ch05_f05-04_component_poly_preview_4x3.png]]

> 최종 builder가 생성한 pseudo-label overlay. 직선과 곡선, 편향된 시점과 교차로를 같은 CULane 형식으로 정리했다.

이 데이터는 사람이 직접 그린 ground truth가 아니라 맵의 색상과 geometry를 이용해 만든 pseudo-label이다.

형식 검증을 통과했다고 해서 모든 선이 의미적으로 정확하진 않았지만, 이제는 설정과 manifest만 있으면 같은 기준으로 레이블과 학습 목록을 다시 만들고, 제외 이유와 overlay까지 함께 확인할 수 있다.

수천 장의 이미지를 단순히 모아둔 상태에서, **학습에 사용할 수 있고 다시 생성할 수 있는 데이터셋**으로 변환되도록 파이프라인을 구축했다.

## 마치며

수천 장의 이미지가 사람 손 없이 그대로 학습 데이터셋이 되는 걸 보니 꽤 뿌듯하다. 데이터 수집부터 추출 방식 비교, 빌더 정리까지 몰아서 진행했는데, 이제 현장 데이터가 새로 생겨도 같은 기준으로 데이터셋을 다시 만들 수 있게 됐다.

물론 이건 어디까지나 pseudo-label이다. 형식 검증을 통과했다고 해서 선이 의미적으로 다 맞다는 보장은 없어서, 결국 학습을 돌려봐야 알 수 있을 것 같다.

아무튼 fine-tuning 준비는 끝났다. 다음엔 이 데이터셋으로 CLRKDNet을 학습시켜서, 거의 반응이 없던 pretrained 모델이 우리 맵에 반응하게 바뀌는지 확인해보겠다.
