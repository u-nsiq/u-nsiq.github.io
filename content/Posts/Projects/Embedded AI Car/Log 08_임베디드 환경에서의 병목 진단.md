## 들어가며

[[Log 07_Local Tangent 기반 조향 설계|지난 포스팅]]에서 드디어 자동차가 실주행 테스트를 했고, 이탈 없이 내 의도대로 주행을 했다.

근데 그 이후에 주행 테스트를 반복하면서 또 새로운 문제를 발견했다. 주행이 길어질수록 반응이 점점 둔해졌다. Low-voltage 경고가 뜨더니, 쓰고 있던 Raspberry Pi 원격 연결이 끊기는 일도 있었다. (배터리 부족 문제는 아니었다)

임베디드 환경은 사실상 처음 다뤄보는 거라 솔직히 어디부터 확인해야 할지도 몰랐다.
일단 모터가 전력을 많이 쓰는 건지, 주행 스크립트에 포함된 overlay 코드가 무거운 건지, 아니면 CLRKDNet FP32 모델 자체가 Pi에 과한 건지부터 하나씩 나눠보기로 했다.

---

## 1. 주행 시간이 늘수록 느려지는 Loop

첫 motor-on 스크립트에는 실험을 확인하기 위한 기능이 여럿 들어 있었다.
카메라 원본과 overlay를 저장하고, 화면에는 lane과 조향값, 좌우 모터 출력을 함께 표시했다.

그래서 실험을 위한 부가적인 기능들을 스크립트에서 하나씩 꺼보면서 병목 진단을 해봤다. 일단 이미지를 저장하는 기능이 문제인지부터 테스트해봤다.

![[embedded_ai_car_log08_latency_drift.png]]

> 이미지 저장을 끈 세 주행 세션의 실제 inference latency. 회색 점은 프레임별 측정값, 파란 선은 15-frame 이동 중앙값이며 우측에는 초반·후반 각 30 frame의 평균을 표시했다.

가장 긴 58초 세션에서는 초반 약 331ms이던 inference가 후반 약 414ms까지 늘었다. 다른 두 세션에서도 증가 폭은 달랐지만 같은 방향의 변화가 나타났다. 조향 계산이 갑자기 복잡해진 것이 아니라, 실행을 이어갈수록 한 프레임을 처리하는 시간 자체가 길어진 셈이다.

근데 이 결과만으로 이미지 저장 기능이 원인이 아니라고 단정할 수는 없었다. 저장을 끈 후반 설정에서도 내부적으로 overlay를 그리고 화면을 출력하는 과정은 남아 있었기 때문이다.

다른 원인을 더 파악해야 했다.

---

## 2. 디버그 기능을 걷어낸 최소 Runtime

### 2.1. 주행 경로와 Telemetry

새 스크립트에서는 화면 출력, overlay 생성, 이미지·동영상 저장과 Jupyter 실행을 모두 제거했다.
실제 주행에 필요한 경로만 남기면 다음과 같다:

```text
Camera → FP32 inference → Decoder → Steering → Motor
```

대신 각 프레임의 처리 시간과 함께 다음 상태를 CSV로 기록했다.

- CPU 사용률과 온도
- ARM clock
- 전처리·추론·전체 pipeline latency
- `vcgencmd get_throttled` 상태

### 2.2. 한 조건씩 다시 시작하기

각 조건은 한 번에 하나만 바꾸었다.
실행이 끝나면 결과를 회수하고 온도와 throttling 상태를 확인했다. Pi의 열을 에어컨 바람에 식히고, 이전 이력이 남아 있으면 재부팅해 `0x0`으로 돌아온 것을 확인한 뒤 다음 조건을 시작했다.

```text
조건 실행 → 로그 확인 → 냉각·필요 시 재부팅 → 상태 확인 → 다음 조건
```

이 방식으로 모터를 끈 추론을 다시 실행하자, 디버그 기능이 하나도 없는 상태에서도 같은 변화가 나타났다.

![[embedded_ai_car_log08_thermal_drift.png]]

> 모터를 끄고 FP32 추론만 반복한 실행의 온도와 inference latency. 온도가 80°C를 넘어선 뒤 열 제한 상태가 나타났고, 후반부의 inference도 초반보다 길어졌다.

처음 15초 동안 약 282ms였던 inference는 마지막 15초에 약 389ms까지 늘었다. 온도는 80°C를 넘었고 thermal throttling도 기록됐다.

화면이나 파일 저장을 지웠는데도 현상이 재현됐으므로, 디버그 기능만으로 설명하기는 어려웠다.

## 3. Motor와 Inference 부하 분리

이어서 1) 모터만 구동하는 조건, 2) 모터를 끄고 레인모델 추론만 수행하는 조건, 3) 두 부하를 합친 최소 주행 조건으로 나누어 비교했다.

| 실행 조건                     | 대표 결과                                                  | 해석                        |
| ------------------------- | ------------------------------------------------------ | ------------------------- |
| Motor only, 90초           | CPU 1.3%, 50.5→53.2°C, throttling 없음                   | 모터 단독으로는 문제가 재현되지 않음      |
| FP32 inference only, 180초 | 추론 약 360ms, CPU 약 99%, thermal throttling              | 모델 추론만으로 CPU와 열 한계에 도달    |
| Minimal drive, 161초       | pipeline 약 382ms, 2.65fps, 최대 87.8°C, under-voltage 이력 | 추론 부하에 모터가 더해지며 전원 여유도 감소 |

![[embedded_ai_car_log08_load_isolation.png]]

> 세 조건의 실제 telemetry. 각 실험의 시작 온도가 같지 않으므로 열 성능의 정밀 비교가 아니라, 어떤 부하에서 문제가 재현되는지를 구분하는 데 사용했다.

모터만 90초 동안 움직였을 때는 온도와 CPU 사용률이 낮게 유지됐고, 저전압이나 열 제한도 나타나지 않았다. 반대로 모터가 없어도 FP32 모델을 연속으로 실행하면 CPU가 거의 포화되고 온도가 80°C를 넘었다.

최소 주행에서는 여기에 모터 부하까지 더해지며 under-voltage 이력이 남았다.

원격 연결이 끊긴 원인을 이 로그만으로 하나로 확정할 수는 없지만, 적어도 모터나 디버그 기능들의 오버헤드 문제가 아닌 **FP32 추론이 계산과 열 여유를 먼저 소모한 상태에서 전원 부하까지 겹친 상황**인 것은 확실했다.

## 4. Thread 수와 남지 않는 시스템 여유

ONNX Runtime의 thread 수를 줄이면 CPU와 열 여유를 만들 수 있지만, 조향 갱신은 더 느려진다.

반대로 thread를 늘리면 latency는 줄어들지만 다른 perception(YOLO 등) 모듈이 사용할 CPU가 남지 않는다.

| Threads | 평균 inference | 평균 CPU | 판단 |
|---:|---:|---:|---|
| 1 | 712ms | 28.5% | 안정적이지만 주행 제어에는 너무 느림 |
| 2 | 458ms | 52.5% | CPU 여유는 있으나 반응성이 부족함 |
| 3 | 376ms | 77.0% | FP32 기준선으로 사용할 수 있는 절충안 |
| 4 | 362ms | 98.0% | 14ms를 줄이는 대신 CPU가 거의 포화됨 |

![[embedded_ai_car_log08_thread_tradeoff.png]]

> Thread 수에 따른 FP32 inference latency와 CPU 사용률. 3개에서 4개로 늘릴 때 속도 이득은 작지만 CPU 여유는 크게 줄어든다.

Thread 3은 FP32를 계속 사용한다면 임시 기준으로 둘 수 있었다. 근데 이 설정도 thermal throttling을 막지는 못한다. 앞으로 같은 Pi에서 표지판과 신호등 인식까지 실행해야 하는데, Lane model 하나가 이미 대부분의 계산 자원을 쓰고 있는 것이다.

한 마디로 설정값을 세밀하게 조정하는 수준으로 해결될 문제가 아니었다. 병목은 명확하게 모델 추론이고, 전체 시스템이 사용할 계산 여유를 먼저 만들어야 한다.

## 마치며

전원이랑 온도, throttling 이력까지 뒤져본 건 이번이 처음이다.

사실 레인 모델 구현하면서 임베디드 환경에서의 프로젝트라는 걸 체감하고 있지 못했는데, 이 병목 진단 덕분에 과목 이름에 왜 '임베디드 최적화'가 들어가는지 제대로 체감했다.

그리고 CPU 쿨링이 왜 중요하다고 하는 지도 확실하게 알았다. (Pi 보드에 있는 CPU 만져봤다가 쿨링 존재의 이유를 알게 되었다)
