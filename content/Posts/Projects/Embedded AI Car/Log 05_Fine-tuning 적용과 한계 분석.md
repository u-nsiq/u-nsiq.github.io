## 들어가며

[[Log 04_Label Pipeline 구축하기|지난 포스팅]]에서는 프로젝트 맵의 노란 선을 CULane 형식의 polyline으로 바꾸고, 수천 장의 이미지를 같은 규칙으로 처리할 수 있는 데이터 파이프라인을 만들었다.

이제 다음을 확인해야 한다:
- CULane으로 학습된 CLRKDNet을 프로젝트 맵 데이터로 fine-tuning하면 맵의 레인을 인식할 수 있을까?
- 그리고 그렇게 얻은 출력은 자동차가 따라갈 주행 기준으로도 사용할 수 있을까?

이번 단계에서는 모델을 학습한 뒤 저장 이미지, Raspberry Pi의 연속 카메라 입력, 실제 주행 시점 데이터 순서로 검증 범위를 넓혔다.

---

## 1. 맵 데이터 Fine-tuning

일단 파인튜닝에 쓰인 데이터 수 자체는 9,052장이다. (그동안 미리 현장에서 추가로 데이터를 집중적으로 수집해놨다)

9,052장의 데이터에 pseudo-label을 이전에 만들었던 빌더로 레이블링하고, 이걸로 전체 모델을 fine-tuning했다. 이 중 7,241장은 학습에, 1,811장은 validation에 사용했다.

Validation의 최고 `F1@50`은 약 0.476이었다. 낮은 지표기는 하지만, 이를 모델의 실제 주행 성능을 나타내는 절대적인 점수라기보다 학습이 정상적으로 진행되고 있는지 확인하는 내부 지표로만 사용했다.

![[embedded_ai_car_log05_initial_finetune_compare.png]]

> Pretrained 모델은 프로젝트 맵에 거의 반응하지 않았지만, fine-tuning 이후에는 노란 레인 방향으로 후보가 나타났다. 위 장면에서는 양쪽 경계를 찾았고, 아래 교차로 장면에서는 한쪽 경계만 남았다. Domain adaptation의 가능성과 아직 남은 한계를 함께 보여준다.

대표 holdout 16장에서 pretrained 모델은 한 장에서도 lane candidate를 만들지 못했다.
근데 재학습한 fine-tuned 모델은 14장에서 한 개 이상의 후보를 출력했다. 후보 대부분도 맵의 노란 선 방향에 놓였다.

fine-tuning의 첫 번째 목표였던 **프로젝트 맵에 반응하는 모델 만들기**는 성공했다.

## 2. Lane Candidate에서 주행 기준까지

### 2.1. Offline Postprocess 검증

CLRKDNet은 조향각이나 모터 속도를 직접 출력하지 않는다. 한 프레임에서 여러 lane candidate와 각 후보의 좌표를 반환할 뿐이다. 이를 주행에 사용하려면 차량 가까운 영역의 왼쪽과 오른쪽 경계를 정하고, 두 선 사이의 위치와 진행 방향을 하나의 제어 기준으로 바꾸어야 한다.

처음에는 다음과 같은 단순한 후처리 규칙을 구성했다.

- 이미지 중심을 기준으로 왼쪽과 오른쪽 lane candidate를 구분한다.
- 양쪽 레인이 있으면 두 선 사이의 중심을 주행 기준으로 사용한다.
- 한쪽 레인만 있으면 예상 차로 폭만큼 offset을 적용한다.
- 어느 쪽도 찾지 못하면 `lost` 상태로 두고 정지한다.

![[embedded_ai_car_log05_postprocess_example.png]]

> 한쪽 lane candidate에 일정한 offset을 적용해 비교적 자연스러운 목표 중심을 만든 사례. 일부 저장 이미지에서는 이 규칙이 작동했지만, 곡률과 카메라 시점이 달라져도 같은 offset을 사용할 수 있는지는 별도의 문제다.

722프레임의 저장된 시퀀스에서 이 규칙을 먼저 점검했다. 대표 장면만 보면 한쪽 레인으로도 충분히 주행 중심을 만들 수 있을 것처럼 보였다.

근데 전체 결과는 안 좋게 나왔다. 양쪽 레인을 함께 얻은 경우는 274프레임이었고, 388프레임에서는 한쪽 레인에 의존해야 했다. `lost`도 60프레임 발생했다.

### 2.2. Raspberry Pi Preview 검증

Fine-tuned 모델을 ONNX로 변환한 뒤 Raspberry Pi 카메라에 연결했다.
처음부터 모터를 구동하지 않고, `preview mode`에서 인식 결과와 계산된 주행 중심만 확인했다.

![[embedded_ai_car_log05_runtime_grid.png]]

> Motors-off preview에서 나타난 대표적인 실패 양상. 레인이 보이는데도 후보가 사라지거나, 곡선에서 여러 후보가 겹치고, 곡선과 교차로에서 한쪽 경계만 남는 장면이 반복됐다.

총 437프레임의 상태를 정리하면 다음과 같았다.

| 상태 | 프레임 수 | 비율 |
|---|---:|---:|
| 양쪽 레인 | 9 | 2.1% |
| 왼쪽 레인만 검출 | 228 | 52.2% |
| 오른쪽 레인만 검출 | 23 | 5.3% |
| 레인 소실 | 177 | 40.5% |

양쪽 레인을 함께 얻은 경우는 9프레임뿐이다. 251프레임은 한쪽 레인에 의존해야 했고, 177프레임에서는 출력이 사라졌다.

모델이 노란 선에 전혀 반응하지 않는 것만이 문제는 아니었다.
곡선에서는 후보가 실제 선 위에 있어도 한쪽 경계만 남아 고정 offset의 의미가 달라졌고, 교차로나 삼거리에서는 화면에 들어온 여러 노란 분기 가운데 어느 선이 현재 주행 경계인지 판단하기 어려웠다. 같은 구간에서도 `left_only`, `both`, `lost`가 바뀌면 계산된 중심 역시 자연스럽게 이어질 수 없었다.

정지 이미지에서 레인을 검출하는 데에는 성공했지만, 그 출력을 **연속적인 주행 기준으로 유지하지는 못한 것**이다.

그래도 아직 이 결과 하나만으로 모델 자체가 문제라고 단정할 수 없었다. 학습 데이터의 시점, pseudo label의 형태, 후보 선택 후처리와 runtime 입력 조건이 모두 원인 후보였다.

먼저 기존 데이터가 실제로 움직이는 자동차의 카메라 시점을 충분히 포함하지 못했다는 가설부터 확인하기로 했다.

## 3. 주행 시점 데이터로 다시 Fine-tuning

### 3.1. 주행 시점 데이터 수집

앞선 데이터에는 자동차를 장면별로 배치해 촬영한 이미지와 특정 구간을 원격 조종하며 저장한 이미지가 함께 들어 있었다. 다양한 맵 장면을 학습하는 데에는 도움이 됐지만, 실제 주행처럼 카메라 시점이 연속적으로 변하고 한쪽 레인이 화면을 크게 차지하는 분포와는 차이가 있을 수 있다고 생각했다.

그래서 자동차를 직접 조종하는 동안 약 0.2초 간격으로 frame을 저장하는 수집 도구를 만들었다. Log 04에서 만든 파이프라인을 재사용해 원본 이미지뿐 아니라 HSV mask, CULane polyline, 검토용 overlay와 manifest까지 함께 남겼다.

![[embedded_ai_car_log05_capture_triptych.png]]

> 수동 조종 중 저장한 실제 주행 시점의 원본, 색상 mask, 자동 생성 label. 카메라가 중앙에 고정된 장면뿐 아니라 한쪽 레인이 크게 보이는 곡선과 시점이 흔들리는 구간도 포함됐다.

수집된 원본은 1,810장이었다. 파일과 레이블을 다시 대조해 빈 레이블이 있는 frame을 제외하고, overlay를 검토해 명확하게 잘못된 사례를 추가로 제거했다. 최종적으로 1,679장을 추가 학습에 사용했다.

### 3.2. 추가 Fine-tuning

이번에는 pretrained weight에서 다시 시작하지 않고, 기존 맵 데이터로 fine-tuning한 모델을 출발점으로 두었다.

아래의 질문이 이 추가 fine-tuning 실험의 목적이다:

> *"실제 주행과 가까운 시점의 데이터를 보강하면 레인 후보가 더 정확하고 안정적으로 바뀌는가?"*

먼저 학습에 사용하지 않은 32장의 이미지에서 기존 모델과 추가 학습 모델을 같은 조건으로 비교했다.

![[embedded_ai_car_log05_additional_finetune_compare.png]]

> 직선 장면에서는 추가 학습 후 후보가 pseudo label에 가까워졌다. 반면 곡선 장면에서는 후보가 실제 노란 선 위에 놓이더라도 서로 다른 직선 조각처럼 벌어져 전체 곡선 geometry를 안정적으로 표현하지 못했다.

32장에 대한 비교 결과는 다음과 같았다. 아래 점수는 공식 CULane metric이 아니라, 같은 pseudo label을 기준으로 두 모델을 비교하기 위한 내부 지표다.

| 비교 항목 | 기존 fine-tuned 모델 | 주행 데이터 추가 후 |
|---|---:|---:|
| 상대 matching score | 0.486 | 0.488 |
| 평균 위치 오차 | 17.88px | 12.52px |
| 프레임당 평균 후보 수 | 3.91개 | 3.75개 |

평균 위치 오차는 줄었고, 비교 이미지에서도 추가 학습 모델의 후보가 노란 선에 더 가까워진 장면이 보였다. 실제 주행 시점 데이터의 보강은 확실히 효과가 있긴 있었다.

근데 상대 matching score는 거의 변하지 않았다. 후보 수 역시 줄었지만 출력의 품질이 좋아졌다고 볼 수는 없었다.

한 장의 이미지에서 선이 노란 영역에 가까워졌다는 사실만으로는, 곡선과 교차로를 지나는 동안 같은 좌우 경계와 방향이 유지되는지 알 수 없었다. 데이터 보강은 선에 반응하는 정도와 위치를 개선했지만, 주행 기준의 안정성까지 해결하지는 못했다고 볼 수 있다.

## 4. 연속 시퀀스에서 드러난 주행 기준의 불안정성

학습에서 분리해둔 734프레임의 주행 시점 시퀀스를 두 모델에 같은 순서로 입력했다.

![[embedded_ai_car_log05_sequence_replay.png]]

> 저장된 시퀀스의 대표 장면. 대부분의 장면에서는 후보가 실제 노란 선을 따라 나타났지만, Frame 277에서는 두 모델 모두 후보를 내지 못했다. 후보가 차선 위에 있다는 사실만으로 차량 가까운 좌우 경계와 하나의 진행 방향이 정해지는 것도 아니었다.

추가 학습 후 후보가 하나도 없는 프레임은 13장에서 7장으로 줄었다. 모델이 실제 주행 시점의 노란 선에 더 자주 반응하게 된 것이다. 근데 최대 4개의 후보가 모두 남은 프레임은 684장에서 705장으로 늘었다. 이 값은 후보의 개수일 뿐 geometry의 품질을 직접 측정하지는 않지만, 추가 학습만으로 **출력이 더 단순하거나 명확해지지는 않았다**는 점은 보여줬다.

프레임을 장면별로 살펴보면 문제는 후보의 개수보다 그 의미다.
곡선에서는 후보들이 노란 선 주변에 있어도 차량 가까운 부분의 기울기와 길이가 서로 달랐다. 대표 교차로 장면에서는 실제 양쪽 경계가 보이는데도 한쪽에만 강하게 반응했다. 여러 분기가 동시에 보이는 삼거리에서는 서로 다른 노란 선이 모두 시각적으로 타당한 후보가 될 수도 있었다.

한쪽 레인만 남으면 앞에서 만든 고정 offset에 의존해야 했고, 같은 offset도 곡률과 원근에 따라 다른 위치를 가리켰다. 후보가 사라지는 프레임이 끼어들면 이전 프레임과의 주행 기준도 끊겼다. 생각해 보면 후보가 실제 차선 위에 있다는 것과, 그 후보가 시간적으로 안정적인 조향 기준이라는 것은 서로 다른 문제였다.

참고로 이 추가 학습 모델은 다시 ONNX로 변환해 Raspberry Pi에 올리지 않았다. 여기까지는 32장의 holdout과 734프레임의 저장된 시퀀스에서 수행한 offline 검증 결과다.
이미 이 단계에서 데이터 부족만으로 전체 현상을 설명하기 어렵다고 판단했기 때문에, 실차에 연결하기 전에 모델이 어떤 geometry를 정답으로 배우고 있는지부터 다시 검토하기로 했다.

Confidence threshold를 높이면 필요한 후보까지 사라졌고, 낮추면 같은 선 주변의 후보가 늘었다.
사실 Detector 설정과 후보 선택 규칙을 더 조정할 수도 있었지만, 그 전에 더 근본적인 질문을 던질 필요가 있었다.

## 5. Full Geometry에서 Near-field Direction으로

이 시점에는 CLRKDNet을 교체하고 색상 mask를 직접 예측하는 segmentation 모델이나, 이미지에서 조향 방향을 바로 회귀하는 모델로 넘어가는 선택지도 고민했다.

하지만 fine-tuning 결과는 CLRKDNet이 프로젝트 맵의 노란 선을 배울 수 있다는 가능성을 보여줬기 때문에, 바로 모델을 버리기 전에, 우리가 어떤 선을 정답으로 가르쳤는지부터 다시 확인했다.

기존 pseudo label은 화면에 보이는 노란 선의 **전체 형상**을 최대한 그대로 polyline으로 표현했다. 일반 도로의 lane detection이라면 자연스러운 목표지만, 생각을 해보면 이 프로젝트의 작은 실내 맵의 주행에는 불필요하거나 모호한 정보도 많았다.

*근데 Lane detection 모델이라고 해서, 화면에 보이는 레인의 전체 geometry를 꼭 복원해야 할까?*

예를 들어:
- 곡선에서는 멀리 있는 곡률까지 정확히 복원하지 않아도 차량 가까운 방향만 알면 된다.
- 교차로나 삼거리에서는 여러 분기가 모두 올바른 노란 선이므로, lane model만으로 어느 방향을 선택할지 결정하기 어렵다.
- 한쪽 레인만 보일 때도 전체 차로 형상을 복원하려 하기보다 현재 선의 위치와 가까운 방향을 안정적으로 얻는 편이 더 직접적이다.

결국 이 프로젝트에서 자동차가 당장 필요로 하는 정보는 다음의 두 가지로 충분하다고 생각했다:

1. 차량 가까운 곳에서 레인이 왼쪽과 오른쪽 어디에 있는가?
2. 가까운 레인이 지금 어느 방향으로 향하고 있는가?

곡선도 짧은 구간만 보면 직선에 가깝게 근사할 수 있다.
이미지 하단의 레인만 직선으로 표현하면 선의 위치는 차량의 좌우 편차를 나타내고, 기울기는 앞으로 진행할 방향을 나타낼 수 있다. 교차로의 회전 방향은 lane model이 모든 분기를 해석하기보다, 표지판 event에 따라 회전한 뒤 다시 레인을 찾도록 분리하는 편이 시스템 구조에도 더 맞았다.

![[embedded_ai_car_log05_target_redefinition.png]]

> 왼쪽의 후보들은 노란 선 가까이에 나타나지만 서로 겹치거나 다른 방향으로 벌어져 하나의 주행 방향을 제공하지 못한다. 오른쪽은 차량 가까운 하단 영역의 위치와 방향만 사용하자는 다음 가설을 개념적으로 표시한 것이며, 모델의 실제 출력은 아니다.

다시 말해, 이 단계에서 세운 가설은 전체 차선 geometry를 더 정교하게 복원하는 대신, 차량 가까운 영역의 위치와 진행 방향을 학습 목표로 삼자는 것이었다.

주행에 필요한 정보부터 더 간단하고 분명하게 정의하면, domain adaptation에서 얻은 장점은 유지하면서 제어에 가까운 출력을 만들 수 있다고 보았다.

## 마치며

이번 fine-tuning 실험을 하면서 느낀 건, domain adaptation 자체가 생각보다 상당히 어렵다는 점이었다. 포스트에는 전부 담지 않았지만, 레이블링 방식을 바꿔보고 데이터를 다시 만들고, 학습 결과를 비교하는 과정을 여러 번 반복했다. 처음에는 아무것도 잡지 못하던 모델이 맵의 노란 선에 반응하기 시작했을 때, fine-tuning만 더 진행하면 어느 정도 해결할 수 있을 거라고 생각했지만, 그렇지도 않았다.

결국 이 단계에서 가장 크게 바뀐 건 모델보다 문제를 보는 방식이다.
Lane detection 모델을 가져왔다고 해서, 원래의 lane detection task를 그대로 풀어야 하는 것은 아니라고 생각해 봤다. 우리 프로젝트가 실제로 필요로 하는 정보만 남기고, 더 쉽고 분명한 문제로 바꿔보는 것도 하나의 해결 방법이라고 생각했다.
